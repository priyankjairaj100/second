# Proposed scientific gates after the complete-service integration pilot

Second: scientific decisions after the V43 engineering gate
Read-only review, 10 October 2026. Repository inspected at 304a9cc73b3c263032f3ef6a02487b4d2df40fbe.
This is a proposal, not a registration or authorization to reuse any old attempt. V43 outcomes are deliberately not assumed. No held-out record files were opened; no model/data inference ran; the repository remained unchanged.

Priority 1: close V43, then establish usefulness of its actual output

V43 can establish complete integration on one exposed development root: 24 stages, 42,467,328 codes, 96 original tokens in three 32-token documents, and actual 64- then 32-token successors. Require every completed arm's actual model bytes and within-representation state bytes to match the independent retained-token oracle, settled resource receipts, and preservation of failed/unstarted attempts. A successful tiny run does not establish realistic-scale cost, quality, statistical superiority, or ACL readiness.

Its target is different from the quality-validated historical target. The implemented metric is H = 0.01 I + X X^T / N_original. Equivalently, after removing a common scalar it uses X X^T + (0.01 N_original) I. Thus changing original normalization changes relative regularization, not just the target identifier. Relative to the retained empirical covariance, effective ridge is 0.01 N_original / N_retained: V43 gives 0.015 and 0.03, whereas the old 128/256 quality model gives 0.02. Context length, source membership, and features also change. Do not renormalize after deletion or transfer old quality guards to V43's new model.

The strongest existing quality result is already a prospectively frozen bounded-pool confirmation: fixed128/normalization256 versus matched sequential128 on forty previously unexposed WikiText validation articles, 5,080 predictions per model. Fixed/sequential PPL ratio was 0.988670203967; the one-sided mixture-bootstrap upper ratio was 1.001859166913 (passes the 1.05 tolerance but exceeds one). Fixed/full-precision ratio was 1.150779689203. This supports that specific tolerance and leaves a material full-precision gap. It is neither superiority nor population-wide confirmation. All sixty prepared validation articles are now exposed and excluded from future untouched evaluation. V39/V40 normalization1664 experiments concern only the first QKV stage and add no full-model quality evidence.

Before spending a new untouched pool, generate a matched sequential comparator for V43's final 32-token state using the same source tokens, checkpoint, original normalization96, ridge, dyadic grids, order, and tie rule. Evaluate that pair plus nearest rounding and full precision on the already exposed eight development articles. This is a cheap diagnostic gate with fresh registration, not confirmation. Retain the historical 1.05 aggregate/1.20 article tolerances as explicit proposed development guards rather than tuning after seeing losses. A bad tiny quality result is evidence about this target, not a reason to loosen the guard. If the 32-token endpoint is unusable, do not advertise its timing as useful-model performance.

Priority 2: one decisive larger, independent full-model development root

Propose thirteen distinct, previously unused C4 English training documents, each with a fixed 128-token prefix: original normalization1664, then delete one whole document (1536 retained tokens), then six more whole documents from that actual successor (768 retained tokens). This connects the full-model question to the two V40 retention regimes and tests the complete wide stages. Use a pinned bounded C4 sampling frame, outcome-blind hash ordering, and exclusion by document IDs, normalized text hashes and prepared token hashes against all historical calibration, quality, and reserved pools. The existing C4 revision recorded in pilots/v10/reserve-source-metadata.json is 1588ec454efa1a09f29cd18ddd04fe05fc8653a2; verify the chosen file/range hashes again before registration. A shard prefix is a bounded frame, not a corpus-uniform sample. No root may be replaced after an adverse result.

Use the same complete cached-lossless, compressed40-with-charged-replay, hybrid native-Gram, and cold full-state controls, plus the independent fresh oracle. Select solver routes before measuring and give compatible optimizations to all arms. Count actual successor storage including tokens/provenance/trust sidecars and common checkpoint, original preparation, source access for deleted Gram contributions, failures, serialization, disposal, and actual sequence lifetime. Report losses against either cached or hybrid even if cold is slower. Do not average first-stage ratios into full-model claims.

A metadata-only call to the current V43 dispatcher on the published 24-stage normalization1664 manifest admitted point, box, and hybrid shapes at original1664 and retained1536/768. For 1664 and1536, the maximum selected solver-plus-dispatch array envelope is 4,519,108,608 bytes; the declared 4-GiB other-residency allowance brings this known subtotal above8 GiB. Point work is 428,146,311,168 / 419,270,639,616 / 321,015,398,400 proxy units; box+point-fallback work is 856,292,622,336 / 838,541,279,232 / 609,840,488,448. These numbers only check structural policies. They exclude Gram preparation, feature extraction, all interpreter overhead, and practical completion. They do not authorize V43's tiny CPU ceilings for a larger run.

Implement this in a fresh research version: V43 hardcodes three sources, 24 stages, normalization96, two fixed memberships, and max_sources=3 for Grams. Re-review all-stage live residency, thirteen-source Gram construction, source replay, target/schema bounds and complete request CPU limits. Use measured V43 components only to form conservative new ceilings, never as reported larger-workload timing. A separate engineering stress check on already exposed inputs may establish resource feasibility first; it cannot substitute for the independent-root experiment.

Priority 3: real second model, then untouched quality on frozen useful models

Use openai-community/gpt2 as the first second checkpoint. The repository catalog pins 607a30d783dfa663caf39e06633721c8d4cfcd7e; pin and verify the actual config, tokenizer and complete safetensors before use. The current official config confirms twelve layers and width768, while the existing repository config preflight derives 48 quantized stages and84,934,656 codes. This doubles depth while preserving supported GPT-2 geometry; it is a genuine second checkpoint, not architecture diversity or modern large-LLM generality. The old v10 planner's refusals concern an earlier representation and neither admit nor prove infeasibility of the new service. Replace DistilGPT2-only hash/stage/extent assumptions in a new version; re-admit the complete model and run actual exact CPU reconstruction/state audits before claiming transfer. Do not label a second-model GPU likelihood run alone a second-model repair experiment.

Use the cluster GPU for quality evaluation only. Import already certified CPU code tensors with exact tensor-word checks; keep embeddings, normalization, biases, weight orientation and tied output head faithful to the declared evaluator. Validate a float64 GPU evaluator against the existing NumPy evaluator on exposed examples and all four model types before any untouched evaluation (propose the historical absolute mean-NLL tolerance1e-8, frozen in advance). Disable approximation changes such as AMP/TF32; if parity cannot meet the frozen gate, use the existing CPU evaluator. GPU likelihood is ordinary numerical evaluation, not certified target computation. Exact feature construction, Gram algebra, code decisions and canonical-state equality stay in the reviewed CPU runtime.

Concrete quality proposal after larger-model development passes: prospectively select64 previously unexposed complete WikiText-2 test articles with at least512 tokens, one512-token prefix each, no BOS/EOS or cross-document context. First audit test-split metadata against every exposure and reserve; do not assume its name guarantees freshness. If fewer than64 eligible articles exist, refuse and revise the protocol before any evaluation. For each final768-token model, compare fixed-anchor calibration against freshly generated matched sequential calibration, with full precision and nearest rounding as descriptive controls. Primary endpoint: pooled next-token NLL/PPL ratio, paired by whole document, with a frozen one-sided bootstrap upper1.05 tolerance and transparent article tails. Sixty-four is a bounded-pool design choice, not a demonstrated power calculation; size and uncertainty requirements must be frozen using development variability before exposure. For two checkpoints, define one conjunction or prespecified multiplicity treatment; never promote whichever passes. Keep calibration-root variability separate from article-mixture uncertainty.

Evaluate only one representative fixed model after all storage arms have proved exact code equality; evaluating identical cached/compressed/hybrid codes repeatedly adds no quality evidence. Add a separately pinned, previously unexposed C4-validation document pool for domain transfer under its own prospective design. WikiText-103 shares WikiText evaluation material and is not an independent domain. A LAMBADA last-word endpoint could later extend utility, but its scorer and exact-match/tokenization contract need validation before using reserved examples; it is not required before answering the current larger-root question.

Priority 4: claims that still remain after these gates

1. Useful frontier: test strong source-local lossless codecs against the uncertain codec on existing development factors, with decoding, trust and complete-state cost; freeze a codec/precision policy before confirmation. Do not treat savings in selected factor payloads as deployment savings. Measure precision versus certificate/refusal/replay behavior to show what the certificate contributes beyond caching and ordinary compression.
2. Reliability/lifetime: multiple disjoint roots and longer actual deletion sequences, balanced randomized method order within root, repeated transactions, and uncertainty at the root/sequence unit. A pair of deletions from one root is correlated and supplies no reliable speedup interval. Predeclare tolerances and worthwhile storage/latency endpoints; if no useful full-model frontier survives strongest controls, redesign the representation or narrow the paper.
3. Closest theorem/implementation comparison: ExecCert's certificate/decision/lifetime ingredients overlap; Exact-Fun's full author proof has now been recovered and read; see docs/LITERATURE_UPDATE_V43.md for its probabilistic assumptions and the pinned source. The candidate distinction is exact adaptive calibration-code recovery for every feature matrix contained in uncertain stored evidence. Fixed features, sufficient statistics, caching, or quantization stability alone are not the novel claim. Preserve conditional arithmetic/provenance/fallback assumptions and distinguish calibration membership from pretraining unlearning.
4. Reproducibility/manuscript: retain actual model/state binaries and receipts, provide a supported runtime plus complete storage and execution costs, map each claim to evidence, preserve all failures/exclusions, and write limitations. A second GPT-2-family model plus one bounded quality pool would improve evidence but does not by itself make an ACL submission strong.

Decision order: audited V43 -> exposed quality diagnostic and larger-root resource review -> independent full-model1536/768 development sequence -> real GPT-2 transfer -> frozen untouched quality and randomized multi-root confirmation. Quality can proceed independently of whether compression wins latency, provided exact useful output models and matched controls are ready. No confirmation candidate should be consumed to debug infrastructure or select representations.
