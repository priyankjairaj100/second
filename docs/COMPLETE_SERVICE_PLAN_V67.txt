Decision and precise scope
V63 confirms that adding fixed Zstandard3 alternatives saves only about0.14%
over the already compressed lossless cache. The approximately9% uncertain-state
storage difference therefore warrants a complete modern-lossless service control,
while the practical value remains unestablished. V64 and V66 qualify software;
V65 admits one new outcome-blind root. Combine the missing full modern control
with the disjoint-root development screen to avoid another full adaptive rerun.
Do not expand to other models, roots or quality articles within this phase.

Execution structure to implement and test
Use one fresh preparation, ten one-request workers and one fresh-oracle worker.
The ten workers are five arms x two successive endpoints. Every arm's second
request must read that same arm's actual first successor, except cold, which
rebuilds from retained tokens and does not open predecessor numerical state.
Retain history for audit; claim logical live-state savings, not physical erasure.

Preparation loads one common context, traverses all13 original sources, solves
the common model and serializes all four representations. Modern and legacy use
the same original feature words. Use V66 rebuild with exclusive disk writers.
The fresh oracle traverses each retained set again and writes all representations;
it must not read any preparation/request factors, states or model codes.
Every request must match its fresh oracle's actual complete model bytes and its
representation's actual canonical successor bytes and trust. Verify membership,
source provenance, immutable retained descriptors and exact Gram contribution
lineage. Modern-to-legacy restoration must also equal the fresh legacy state.
Ten comparisons and two fresh retained traversals are necessary, not sufficient,
for the scientific conclusion. Shared numerical implementation remains explicit.

Startup, order and clocks
Use a fresh process/context per request for every arm. Two requests within one
worker would reuse startup differently from the proposed balanced sequence, so
do not reuse V61's worker as-is or transfer old performance numbers. Order the
five arms by a separately frozen hash seed at endpoint1 and reverse at endpoint2;
commit the actual order in registration before any model outcome. Each arm then
occupies complementary positions across endpoints, but endpoint workloads differ:
this is a balanced development schedule, not repeated timing or statistical
counterbalancing sufficient for inference. No arm is selected from observed time.

Sequential afterok jobs on the same admitted CPU host, one thread/affinity; no
cache flushing or privileged operations. Record actual affinity, environment,
start/end and available scheduler co-residence snapshots. Do not claim exclusive
node access. Record native compilation/startup work under controller transaction
and CPU accounting, even if outside operation timers. All arms share the same
runtime installation, including codec imports; report the full physical added
dependency footprint rather than claiming a minimal per-arm deployment build.

Report V66 request clocks plus complete worker/controller clocks; source/runtime
and input verification, context load, admission, receipt writes and shutdown cannot
disappear. Rebuild shares common extraction/model work: attribute it explicitly
to each representation, retain all encoder/canonical-validation/write/disposal
costs, and show unallocated shared overhead. Attributed sums are not independently
measured end-to-end deployment times. Never sum nested clocks or duplicate Slurm
allocation and batch CPU. Failed attempts and audits remain charged separately.

Interpretation and next gates
One new bounded-frame root and one observation per arm/endpoint are development
falsification. No confidence interval or population reliability/speed claim.
All failures, fallback, domination and negative comparisons stay visible. If any
exactness or complete-cost gate fails, do not promote remaining partial output.
If modern/cached/hybrid dominates compression, narrow the practical claim and
reassess contribution. An independently motivated deployment constraint is still
needed to interpret a storage-versus-latency tradeoff as useful.
Untouched paired article-level quality, uncertainty/sample-size justification,
prospective timing replication and final manuscript/bundle validation follow
separately. No conference submission or paid compute is authorized here.
